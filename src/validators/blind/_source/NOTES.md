# Validator notes

Layout: `validators/<domain>.js` are self-contained ES modules, generated by
`node build.mjs` from `src/common.js` (generic helpers) plus `src/<domain>.js`
(`src/usgs.js` serves both USGS domains through a `STRICT` flag). Edit `src/`, then rebuild.
`node check.mjs` checks that every hand-derived correct record passes V2, and that
a format-specific reference program (test scaffolding only) passes V3 within budget.
It also asserts that a few wrong-but-well-formed outputs and defective programs are rejected.

Generic helpers treat `raw` as an opaque string. They include:
- numeric readings of digit runs: plain, Brazilian `1.234,56`, decimal comma, US grouping, and comma-list parts;
- date tokens: ISO with optional time/offset (a space before the offset is allowed), D/M/Y and M/D/Y
  (ambiguous forms are kept both ways), day-monthname-year and monthname-day-year (en/pt/es), and
  10- or 13-digit epoch values;
- loose clock times, which are combined with date-only tokens;
- whole-token identifier search, and an id mutator.

None of them depend on a field name, key order, column position or tag of a specific format.

## financial

V2 (property):
- V0 checks copied.
- `status === "valid"`: the telos fixes status to "valid". A record that should be rejected returns null, so "invalid" is never correct.
- `audit_id` appears as a whole token in raw and has no surrounding spaces ("copied verbatim").
- At least one supported currency is named in raw (codes in any case, real/dolar/euro/libra and variants, R$/US$/$/€/£). Rationale: "missing currency → reject".
- Category follows currency: `domestic` requires BRL evidence and `international` requires evidence of a non-BRL currency ("domestic if BRL, otherwise international").
- `value_in_usd ≈ n × rate` (within 0.0051, which allows rounding to cents). Here n is a positive number in raw, read with any generic number convention, with the id and date tokens masked out. The rate must be the one of a currency named in raw and allowed by the category. Domestic may also use rate 1 when "usd" occurs, which covers the "value already in USD, do not convert again" rule. Rationale: exact rates, Brazilian format, "zero/negative → reject".
- `date` is the UTC calendar date of some date/datetime in raw (offset applied, epoch converted). If no date token is recognised, the year must at least appear. Rationale: "UTC date; missing date → reject".

V3 (metamorphic), at most 6 runs:
- R1: replace the id token with a mutated id. Only `audit_id` may change, and it must equal the new id.
- R2: double the amount token, written in the same number style. Then `value_in_usd` must equal 2n × rate and nothing else may change (linearity of the conversion).
- R3: set the amount token to 0. The output must be null ("amount zero → reject").
- R4: move every date token one day later. `date` must be exactly +1 day, with the other fields unchanged.
- R5: if exactly one currency is named by standalone code/name tokens, swap it (e.g. BRL→EUR, dolar→euro, eur→gbp, case preserved). The value must follow the new rate and the category the new currency.
- R6: remove the currency tokens (only when a single currency is named standalone). The output must be null ("missing currency → reject").

## iot

V2:
- V0 checks copied.
- `status === statusOf(metric, value)`: status is "derived from the canonical value".
- `value` has at most 2 decimals ("rounded to 2 decimals").
- `device_id` appears as a whole token in raw ("copied verbatim").
- The metric is named in raw (temp*/therm*, hum*/umid*/RH, press*/baro*): "missing metric → reject".
- The output zone has evidence in raw: a word (en/pt), a standalone letter N/S/E/W, or vendor zone-A..D. Rationale: "missing zone → reject" and the zone mapping.
- `value ≈ conv(n)` (within 0.005) for some number n in raw, with id and dates masked. Allowed conversions depend on unit evidence:
  - temperature: identity if Celsius is named or no F/K unit is present; F→C if Fahrenheit is named; K→C if Kelvin is named;
  - pressure: identity if hPa/mbar is named, or if no kPa/Pa is present; ×10 if kPa is named;
  - humidity: identity.
- `timestamp_utc` equals an instant justified by raw. That means an ISO datetime with its offset applied (no offset means UTC), a date-only token at 00:00:00, a date-only token combined with a loose time token, or an epoch value in s/ms. If nothing is recognised, the year must at least appear.

V3, at most 5 runs:
- R1: mutate the id. Only `device_id` changes.
- R2: add 1 to the value token (or subtract 1 near the range top), in the same number style. The value must equal conv(n±1) with the conversion found by V2, status must be re-derived, and nothing else may change.
- R3: set the value token to 9999. That is impossible under every allowed conversion, so the output must be null ("physically impossible → reject").
- R4: move every date token one day later. `timestamp_utc` must move by exactly +24h.
- R5: swap the zone token (north↔south, N↔S, E↔W, zone-A↔zone-B, zone-C↔zone-D). This runs only when all zone evidence points to the output zone. Only `zone` may change, to the opposite zone.

## usgs-corrected / usgs-strict

V2:
- V0 checks copied. `baseValid` was not included in `v0-format-validators.js`, so it is reconstructed from the telos field list. It checks: id non-empty string, magnitude finite, `magnitude_type` in the list, lat/lon ranges, timestamp format, place non-empty, `event_type` string, and status reviewed/automatic. Depth and significance use the corrected or original V0 as given.
- `event_id` appears as a whole token. It must not be a strict substring of a longer alphanumeric run, which catches outputting the `code` fragment of `net+code`.
- `magnitude_type` appears in raw case-insensitively as a token (the input magType lowercased).
- magnitude, latitude, longitude and depth each equal a numeric token in raw, each from a distinct token. Lat, lon and depth must also lie within 4 numeric tokens of each other, since the telos describes a coordinate triple. This catches rounded, clamped or substituted values.
- `place` appears verbatim in raw (raw, JSON-escaped or CSV-quoted form). It must not be the "M x.y - place" title when the bare place is also present.
- `event_type` appears verbatim. It must not be a GeoJSON structural word (Feature/Point) and must differ from place and status.
- `status` appears in raw as a word.
- `timestamp_utc` equals the earliest full datetime found in raw, with milliseconds truncated. Rationale: origin time; the `updated` time is never earlier than the origin time.
- Significance, corrected: when a `sig` key with a value is present, `significance` must equal it (null for sig:null). With no `sig` field, `significance` must be null ("null when the source has no such field").
- Significance, strict: a `sig` value must be present and equal. The strict telos requires an integer, so a CSV input (no sig) cannot be converted faithfully, and any integer would be invented.

V3, at most 5 runs:
- R1: mutate the id token (all occurrences). Only `event_id` changes.
- R2: add 1 to the magnitude tokens and change the depth token. Corrected sets depth to `-1.5`, since negative depths are valid and must not be clamped or rejected. Strict uses depth+1. Magnitude and depth must follow; id, coordinates, time and place must not change.
- R3: negate the lat and lon tokens. Latitude and longitude must be negated and everything else unchanged.
- R4: move the origin-time token(s) one day earlier. `timestamp_utc` must move by exactly −24h. The shift is earlier, so the token stays the earliest datetime.
- R5: add 1 to the `sig` value, when present. `significance` must follow.

## Assumptions and limitations

- USGS lat/lon swaps cannot be detected generically: both are numeric tokens and the formats order them differently. The adjacency check only ensures they come from the coordinate group.
- Numeric matching is permissive. It uses any number in raw except id and date tokens, so a wrong output that happens to equal another number × an allowed rate can slip through V2. V3 R2 narrows this by checking that the output follows the specific token.
- A run such as `6.738,16` (grouped thousands with 1-2 decimal-comma digits) is read only as a Brazilian amount, never as the list "6.738, 16". A comma-delimited format with a 3-decimal number followed by a 1-2 digit number would be misread; this is considered rare.
- Financial: a bare `$` is read as USD evidence. "usd" inside a key such as `value_usd` counts as USD evidence, and allows rate 1 for domestic records ("already USD, do not convert again").
- IoT: the metric must be named, following "missing metric → reject". A unit alone (e.g. `°C` or `kPa` with no metric word) does not count as naming it. The one exception is `RH`, which is itself an abbreviation of relative humidity. Single-letter units and zones are recognised only as standalone uppercase tokens (not glued to letters, digits, `-` or `_`).
- When no date token is recognised (an unknown date notation), V2 falls back to requiring the output year to appear in raw, so that correct outputs of new formats are not rejected.
- Metamorphic relations are skipped, and count as passing, when their precondition does not hold. Examples: no unique amount/value token, an ambiguous date that cannot be shifted, or several currencies/zones named.
- V3 treats a crash or a null output on a transformed valid input as a violation. It also compares only the telos fields; extra keys are ignored except in the financial/iot `sameExcept` checks, which compare all keys.
